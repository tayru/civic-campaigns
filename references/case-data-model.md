# Учёт отдельного дела и кампании

Канонический формат — `assets/case-schema.json` от корня пакета. Пустая заготовка — `assets/case-template.json`. Не поддерживай параллельные словари обозначений в отдельных файлах. Версия контракта 0.4; старые записи v0.3 не мигрировать автоматически по буквенным кодам без чтения их значения.

## Иерархия и связи

Один JSON описывает отдельное дело либо связанную кампанию. Поле `campaign` сохраняет историческое имя для совместимости формата 0.4 и служит общей карточкой цели; оно не означает, что заявитель ведёт публичную кампанию. Для отдельного дела не выдумывай команду и стратегию: неизвестные строковые поля оставляй пустыми, `weekly_hours` — `null`. `cases` — самостоятельные объекты/эпизоды; `threads` — ветки обращения или процедуры; `events` — датированные события, в том числе встречи без письма. `sources` — источники; `claims` — утверждения; `actors` — участники по рабочим ролям; `commitments` — обязательства; `outcomes` — результаты и оценка вклада; `actions` — ближайшие действия.

Идентификаторы уникальны внутри коллекции. Ссылки должны указывать на существующую запись соответствующей коллекции. Пустые коллекции допустимы; неизвестная дата или участник — null. Для содержательной записи создавай id, а не заполняй пробел догадкой.

## Краткая карточка вместо полного реестра

Для одного обращения по умолчанию достаточно текста или строки таблицы: заявитель/роль; предмет и требуемый результат; адресат и процедура; отправка/получение/регистрация с источником; полученный ответ и нерешённый вопрос; следующий шаг; юридический срок либо явно рабочая контрольная дата; подтверждение исполнения. Не проси заполнить полный JSON ради подготовки письма.

Несколько независимых дел можно показать отдельными строками обзора, не объявляя их одной кампанией. При запросе машиночитаемого экспорта сохрани отдельный реестр на несвязанные дела либо объясни согласованную структуру; не смешивай источники, сроки и заявителей. Не меняй схему и существующие записи автоматически.

Для общего обзора нескольких реестров используй `portfolio-management.md`, для доски, календаря и хронологии — `portfolio-views.md`. Это представления существующих данных, не миграция контракта 0.4. Учитывай исходный набор вместе с локальным ID, чтобы одинаковые идентификаторы разных дел не перезаписывали друг друга. Признаки внимания и приоритеты вычисляй с явным объяснением, не подменяя ими сохранённые статусы и не добавляя неизвестные схеме поля в JSON.

## Доказательства

Тип источника, статус утверждения, событие и оценка вклада — независимые измерения. Источник содержит `availability`: reviewed / referenced_only / unavailable. `supported` в утверждении требует хотя бы одного реально просмотренного источника; это не означает, что каждое утверждение документа истинно. Конкретную достаточность доказательства оценивает человек/модель, не валидатор.

`source_ids` связывает запись с источниками. Для подтверждённой регистрации нужна дата и источник. Для юридического срока нужны проверенное основание и источник; `working` означает внутреннюю контрольную дату, которую нельзя предъявлять как установленный законом срок. Изменения статуса сохраняй событиями; не стирай прежнюю историю.

## Обязательства и результаты

Для обязательства записывай действие, ответственного участника при известности, статус, срок/условие, источник и ожидаемый след. Предложенное резюме встречи и согласованное обязательство — разные состояния.

У результата отдельно укажи вид, источники и attribution. Уровни и интерпретация — в `outcomes-and-learning.md`. Отчёт о выполнении и независимая проверка — отдельные события. Не существует обязательной линейной лестницы для всех дел.

## Хранение и публикация

Общий реестр содержит рабочие роли и локаторы. Контакты, подписи и закрытые документы хранятся отдельно в согласованном пользователем месте. `visibility` отмечает характер источника, но не осуществляет обезличивание. Автоматического публичного экспорта в пакете нет.

## Проверка

Запускать `python scripts/validate_package.py` для структуры пакета; добавить `--case /absolute/path/to/registry.json` для проверки реестра. Требуется Python 3 и установленный jsonschema; при отсутствии зависимости сообщить, что проверка не выполнена, не устанавливать ничего скрытно.

Валидатор проверяет схему, ссылки, даты и некоторые сочетания полей. Он не устанавливает правоту сторон, актуальность закона, достаточность доказательств или отсутствие персональных данных. Результат PASS относится только к перечисленным машинным проверкам.
